# ArtisanHub — мультивендорный маркетплейс товаров ручной работы

> Этот документ — твоё техническое задание и roadmap. Я буду выступать куратором:
> когда дойдёшь до очередного этапа, присылай код — разберём вместе, найдём баги,
> обсудим архитектурные решения. Не торопись проходить все этапы сразу — лучше
> сделать 3 этапа хорошо, чем 10 наспех.

## Зачем именно эта идея

Твой предыдущий проект (блог с постами и одной подпиской) был *линейным*:
один автор → один пост → одна подписка → один платёж. Здесь всё иначе —
появляется **множественность и согласованность состояний**:

- Один заказ может содержать товары от **нескольких продавцов одновременно**
  → нужно разбивать заказ на под-заказы и синхронизировать их статусы.
- Деньги должны **расщепляться между продавцами и платформой** (комиссия) —
  это уже не "оплатил и всё", а маркетплейс-платёж (Stripe Connect).
- Остатки товара меняются **параллельно** (гонки при одновременной покупке
  последней единицы) — потребуется думать о конкурентности на уровне БД.
- Нужен **real-time** слой (чат покупатель↔продавец, уведомления) — впервые
  выходишь за пределы обычного REST request/response.
- Поиск с фильтрами и фасетами (цена, категория, рейтинг, наличие) —
  первый раз столкнёшься с оптимизацией запросов на масштабе.

Это тот же набор технологий (Django REST + Vue 3/Pinia), но с гораздо более
сложной предметной областью — то, с чем ты реально столкнёшься на работе.

## 0.1 Разделение труда backend/frontend

Ты пишешь только backend — это нормально и правильно, если хочешь расти
именно как бекендер. Фронт я буду делать сам, **но не заранее одним куском**,
а синхронно с бекендом: как только у тебя стабилизируется API одного модуля
(например, каталог), я соберу под него Vue-часть. Причина простая: если я
напишу фронт под API, которого ещё нет, он либо будет угадыванием, либо
придётся полностью переписывать после того, как ты поменяешь контракты
в процессе реализации — а ты их поменяешь, это нормальная часть разработки.

Практический механизм: у тебя в `requirements.txt` уже есть
`drf-spectacular` — используй его с первого API-эндпоинта
(`/api/schema/`, `/api/docs/`). Присылай мне ссылку на актуальную OpenAPI-схему
или просто сериализаторы/вьюхи — я буду собирать фронт по контракту, а не
по догадкам.

## 1. Предметная область

Платформа, где независимые продавцы ("мастерские") выставляют товары
(handmade, digital-товары, услуги), а покупатели формируют один заказ
из товаров разных продавцов, оплачивают его одним платежом, который
затем автоматически распределяется между продавцами за вычетом комиссии
платформы.

### Роли пользователей
- **Buyer** — покупатель: просмотр, избранное, корзина, заказы, отзывы, чат.
- **Seller** — продавец: управляет магазином (Shop), товарами, остатками,
  обрабатывает под-заказы, отвечает в чате, видит аналитику продаж.
- **Admin** — модерация отзывов и магазинов, разбор споров (disputes),
  общая аналитика платформы.

Один пользователь может быть одновременно и Buyer, и Seller (как на Etsy/Ozon).

## 2. Функциональные модули

### 2.1 Каталог и товары (`catalog`)
- Модели: `Shop`, `Product`, `ProductVariant` (размер/цвет/материал — со своей
  ценой и остатком), `Category` (с вложенностью через `MPTT` или `parent`
  self-FK), `ProductImage` (несколько изображений на товар).
- Полнотекстовый + фасетный поиск: фильтры по цене, категории, наличию,
  рейтингу магазина, сортировка (по цене, новизне, популярности).
- Остатки (`stock`) списываются **атомарно** при оформлении заказа —
  без гонок (`select_for_update` или `F()`-выражения).

### 2.2 Избранное (`favorites`)
- Избранные товары **и** избранные магазины отдельно.
- Уведомление, если избранный товар подешевел или скоро закончится
  (Celery-задача, периодическая проверка).

### 2.3 Корзина и заказы (`orders`)
- Корзина хранит позиции из разных магазинов.
- При оформлении заказ **разбивается на под-заказы** (`SubOrder`) — по одному
  на каждый магазин, каждый со своим статусом
  (`pending → confirmed → shipped → delivered → cancelled/returned`).
- Родительский `Order` агрегирует статус (например, "частично доставлен").
- История статусов (`OrderStatusHistory`) — кто и когда сменил статус.
- Отмена заказа покупателем возможна только на определённых статусах —
  нужна явная state machine (можно вручную, можно `django-fsm`).

### 2.4 Оплата (`payments`) — самая сложная часть
- Интеграция **Stripe Connect** (Standard или Express account для продавцов):
  платформа принимает платёж целиком, затем автоматически переводит каждому
  продавцу его долю за вычетом комиссии платформы (`application_fee_amount`).
- Обработка вебхуков: `checkout.session.completed`,
  `account.updated` (статус верификации продавца),
  `charge.refunded`, `payout.paid`.
- Частичные возвраты — если покупатель возвращает товар от одного из
  нескольких продавцов в заказе, а не весь заказ целиком.
- Идемпотентность вебхуков (как в исходном проекте, но с большим числом
  типов событий и партиями выплат).

### 2.5 Подписки продавцов (`subscriptions`)
Не подписка покупателя на контент (как в прошлом проекте), а **тарифные
планы для продавцов**:
- `Basic` — до 10 товаров, комиссия 8%.
- `Pro` — до 100 товаров, комиссия 5%, приоритет в поиске.
- `Premium` — безлимит, комиссия 3%, аналитика, промо на главной.
- Ежемесячное продление через Stripe Subscriptions, downgrade с сохранением
  превышающих лимит товаров как "скрытых" (не публикуются, пока не уменьшат
  количество или не проапгрейдятся).

### 2.6 Отзывы и рейтинги (`reviews`)
- Отзыв можно оставить **только после доставленного заказа** (проверка через
  `OrderItem`).
- Модерация: отзыв уходит в очередь на проверку при жалобе / низкой оценке,
  админ может скрыть.
- Рейтинг магазина — агрегат (пересчитывается через сигнал или Celery-задачу,
  не на каждый GET).

### 2.7 Чат в реальном времени (`chat`)
- Django Channels + WebSocket: диалог покупатель↔продавец, привязанный
  к конкретному заказу или товару.
- Статусы "прочитано/не прочитано", индикатор "печатает".
- Fallback на обычный REST-эндпоинт истории сообщений (для первой загрузки).

### 2.8 Уведомления (`notifications`)
- In-app + email: новый заказ (продавцу), смена статуса (покупателю),
  новое сообщение в чате, товар из избранного скоро закончится.
- Одна модель `Notification` с `type` и `payload` (JSON), не отдельная
  таблица на каждый тип события.

### 2.9 Промокоды и скидки (`promotions`)
- Промокод может быть привязан к конкретному магазину или ко всей платформе.
- Проценты / фиксированная сумма / бесплатная доставка.
- Ограничения: даты действия, минимальная сумма заказа, лимит использований
  (в том числе на одного пользователя).

### Этап 0 — Фундамент (детально)

Разбиваю на подэтапы с конкретными решениями, которые нужно принять

#### 0.1 Гигиена репозитория и зависимостей
- `requirements.txt` сейчас выглядит как результат `pip freeze` из общего/
  глобального окружения, а не чистого venv под этот проект — там
  `firebase-admin`, `google-cloud-storage`, `pycairo`, `paramiko`, `keyring`,
  `pymacaroons`, `PyNaCl`, `jeepney`, `lockfile`, `monotonic` и т.д., которые
  никак не относятся к маркетплейсу. Пересобери зависимости с нуля в чистом
  venv/Docker-контейнере, ставя только то, что реально импортируешь.
- Раздели зависимости хотя бы на `requirements/base.txt`,
  `requirements/local.txt` (дев-инструменты), `requirements/production.txt`
  — или сразу переходи на `pyproject.toml` + `uv`/`poetry`, раз проект новый.
- Добавь сразу, до первого приложения: `pytest`, `pytest-django`,
  `factory-boy`, `ruff` (или `flake8`+`black`), `django-extensions` (удобно
  для `shell_plus`, `graph_models`).
- Заведи `pyproject.toml` или `setup.cfg` с конфигом `ruff`/`pytest`
  (`DJANGO_SETTINGS_MODULE`, `python_files`, `testpaths`) — чтобы `pytest`
  запускался одной командой без флагов.

#### 0.2 Решения, которые нельзя отложить
- **`AUTH_USER_MODEL`** — у тебя в `settings.py` эта строка закомментирована.
  Это единственная настройка Django, которую **нельзя поменять после первой
  миграции** без болезненного пересоздания БД. Реши сейчас: кастомная
  модель `User(AbstractUser)` с полями `is_seller`/`user_type` или отдельная
  модель `Shop(owner=OneToOneField(User))` без изменения `User` вообще.
  Я рекомендую второе — модель `User` остаёть простой, "продавец" — это
  наличие связанного `Shop`, а не флаг. Но это твоё архитектурное решение,
  обоснуй его в комментарии к модели.
- Реши, где будет жить приложение с пользователями: `apps/accounts` или
  `apps/users` — создай структуру `apps/` с `__init__.py`, чтобы все
  будущие приложения (`catalog`, `orders`, `payments`...) лежали в одном
  месте, а не вперемешку с корнем проекта.
- В `settings.py` найден баг, который стоит исправить прямо сейчас:
  ```python
  if DEBUG:
      CORS_ALLOW_ALL_ORIGINS = True
  else:
      CORS_ALLOW_ALL_ORIGINS = [...]   # ← ошибка
  ```
  `CORS_ALLOW_ALL_ORIGINS` — булев флаг в django-cors-headers. Присвоение
  ему списка не даст синтаксической ошибки, но список — truthy, то есть
  **в продакшене (`DEBUG=False`) у тебя фактически включится разрешение
  всех origin** — ровно то, чего ты пытался избежать. Нужно:
  ```python
  if DEBUG:
      CORS_ALLOW_ALL_ORIGINS = True
  else:
      CORS_ALLOW_ALL_ORIGINS = False
      CORS_ALLOWED_ORIGINS = [
          "http://localhost:5173",
          "http://127.0.0.1:5173",
      ]
  ```
  Хороший пример, почему даже конфиг стоит писать так, будто его кто-то
  проверит тестом — здесь баг был бы неочевиден до первого прод-деплоя.
- Убери мёртвую строку `os.getenv('SECRET_KEY')` перед присвоением
  `SECRET_KEY = os.getenv('SECRET_KEY')` — вызов без сохранения результата
  ничего не делает, это забытый отладочный вызов.
- Заранее реши про `ALLOWED_HOSTS` — сейчас хардкод `['localhost', '127.0.0.1']`.
  Сделай через `env`, списком через запятую, чтобы не трогать код при
  деплое на реальный домен.

#### 0.3 Docker и инфраструктура — то, что уже сделано, плюс что доделать
Хорошо: у тебя уже разведены `web`, `db`, `redis`, `celery-worker`,
`celery-beat`, отдельный `static-init` для прав на volume — это грамотный
подход, не все на твоём уровне сразу разносят static-init отдельным
сервисом.

Чего не хватает:
- **Healthcheck** для `db` и `redis` + `depends_on: condition: service_healthy`
  для `web`/`celery-worker` — сейчас `depends_on` просто ждёт старта
  контейнера БД, а не готовности принимать соединения. При холодном старте
  `web` может упасть на первой миграции, пока Postgres ещё инициализируется.
- `.env.example` в репозитории (без реальных секретов) — чтобы куратор
  (я) или ты сам через полгода мог поднять проект по одному файлу.
- Дублирование `build:`/`volumes:`/`env_file:` в пяти сервисах — вынеси
  через YAML-якоря (`&app-base` / `<<: *app-base`), это чище и меньше шансов
  забыть добавить переменную в одном из сервисов.
- В `Dockerfile` командой по умолчанию стоит `gunicorn ArtisanHub.wsgi`,
  но по roadmap на этапе 7 понадобится Channels — тогда `wsgi` придётся
  заменить на `daphne`/`uvicorn` + `ArtisanHub.asgi`. Не делай это сейчас,
  но держи в голове: HTTP и WebSocket в проде часто разносят на два
  разных процесса/сервиса (обычный gunicorn для REST + отдельный ASGI-сервер
  для WS), не пытайся обслуживать всё одним gunicorn worker.

### Этап 1 — Каталог (детально)

По факту `apps/users` (Auth/`CustomUser`) у тебя уже готов с этапа 0 — этот
этап про два новых приложения: `apps/shops` (модель `Shop`, как договорились —
отдельно от `users`) и `apps/catalog` (сам каталог товаров).

#### 1.1 `apps/shops` — сначала это, каталог без него бессмысленен
- Модель `Shop` — код и обоснование полей смотри в переписке про
  `OneToOneField(CustomUser)`, `slug` с авто-генерацией и проверкой на
  уникальность, `rating_cached`/`reviews_count_cached`, `stripe_account_id`
  (пока просто поле, заполнять начнёшь на этапе 4).
- Эндпоинт "стать продавцом": `POST /api/v1/shops/` — создаёт `Shop` для
  `request.user`, если у него его ещё нет (`if hasattr(request.user, "shop")`
  → 400 "У вас уже есть магазин"). Публичный `GET /api/v1/shops/<slug>/` —
  витрина магазина (потребуется на фронте карточка продавца).
- `permissions.py`: `IsShopOwner` — для эндпоинтов редактирования самого
  магазина (`PATCH /shops/me/` — обнови описание/логотип). Отдельно заведи
  `IsShopOwnerOrReadOnly` — он понадобится в `apps/catalog`, но логичнее
  держать его здесь же, рядом с `Shop`, а не размазывать по каталогу.

#### 1.2 `apps/catalog` — модели
```
Category(parent: self FK nullable, name, slug unique, order)
Product(shop FK, category FK, title, slug, description, base_price, is_published, created_at)
ProductVariant(product FK, sku unique, attributes: JSONField, price_override nullable, stock, is_default)
ProductImage(product FK, image, order, alt_text)
```
Детали, которые стоит продумать заранее, а не по ходу:
- **`attributes` как `JSONField`, а не отдельные колонки `size`/`color`.**
  У разных категорий товаров разные атрибуты (у украшения — материал и
  размер, у открытки — вообще ничего). Жёсткие колонки заставят тебя либо
  плодить NULL-поля на 90% товаров, либо городить EAV-таблицы. JSONField —
  осознанный компромисс: теряешь возможность фильтровать по атрибуту на
  уровне БД-индекса "из коробки" (это уже про Postgres `GIN`-индекс на
  JSONB, отдельная тема, не обязательна на этом этапе), выигрываешь в
  гибкости модели. Для MVP этого достаточно.
- **`price_override` на варианте, а `base_price` на товаре** — цена варианта
  необязательна: если у товара один вариант или варианты не отличаются по
  цене, `price_override=None` → используется `base_price` товара. Реши,
  где будет метод `get_effective_price()` — логично на `ProductVariant`,
  чтобы сериализатор не дублировал `variant.price_override or product.base_price`
  в нескольких местах.
- **`is_default` на варианте** — когда на витрине показываешь карточку
  товара со списком, а не детальную страницу, нужно показать одну цену/
  одно фото — бери `is_default=True` вариант. На уровне модели добавь
  `save()`-логику или `signal`, гарантирующую, что у товара всегда ровно
  один вариант с `is_default=True` (либо валидацию в сериализаторе — но
  на уровне модели надёжнее, раз варианты могут создаваться и не только
  через API, а например через админку или management-команду).
- **Остатки (`stock`) — уже сейчас думай о том, что списание будет
  атомарным на этапе 3.** Здесь, на этапе 1, просто поле
  `stock = PositiveIntegerField(default=0)`, ничего специального. Но
  заведи в голове: **не делай** `stock` вычисляемым полем на лету через
  агрегацию заказов — это должно быть хранимое значение, которое
  уменьшается транзакционно при заказе (иначе на этапе 3 придётся
  мигрировать модель).

#### 1.3 Permissions — владение, а не просто "автор"
Отличие от прошлого блог-проекта: там был `IsAuthorOrReadOnly` (сравнение
`obj.author == request.user`). Здесь товар принадлежит **магазину**, а не
напрямую юзеру:
```python
class IsShopOwnerOrReadOnly(BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in SAFE_METHODS:
            return True
        # obj — это Product; владение проверяем через obj.shop.owner
        return obj.shop.owner_id == request.user.id
```
Обязательно напиши тест на это отдельно от happy-path: создай `Shop A`
(owner = user A) с товаром, залогинься под `user B` (у которого свой
магазин или вообще нет магазина), попробуй `PATCH` чужой товар — жди 403.
Без такого теста легко случайно сломать permission при рефакторинге и не
заметить (обычный список/детейл тест на "товар редактируется" пройдёт даже
если permission вообще отключить).

#### 1.4 Сериализаторы — раздели List и Detail с самого начала
Не делай один `ProductSerializer` на всё. В списке товаров тебе не нужны
все `variants` и полное `description` — это лишний вес ответа на каждый
товар в пагинированном списке из 20 штук:
```python
class ProductListSerializer(serializers.ModelSerializer):
    shop_name = serializers.CharField(source="shop.name", read_only=True)
    price = serializers.SerializerMethodField()
    thumbnail = serializers.SerializerMethodField()

    class Meta:
        model = Product
        fields = ["id", "slug", "title", "shop_name", "price", "thumbnail", "is_published"]

    def get_price(self, obj):
        default_variant = obj.variants.filter(is_default=True).first()
        return default_variant.get_effective_price() if default_variant else obj.base_price
```
**Осторожно:** `get_price` выше содержит N+1 сам по себе, если
`obj.variants` не запрефетчен — `.filter().first()` на непрефетченном
related manager всё равно уйдёт в БД отдельным запросом на каждый товар
в списке. Правильно — прокинуть `Prefetch` с уже отфильтрованным
queryset'ом на уровне вьюхи:
```python
from django.db.models import Prefetch

queryset = Product.objects.select_related("shop", "category").prefetch_related(
    Prefetch("variants", queryset=ProductVariant.objects.filter(is_default=True), to_attr="default_variant_list"),
    "images",
)
```
и в сериализаторе брать `obj.default_variant_list[0]` вместо `obj.variants.filter(...)`.
Это тонкий момент, специально дал тебе его продумать — типичная ошибка:
"я же сделал prefetch_related('variants'), почему всё равно N+1?" — потому
что `.filter()` поверх уже загруженного `prefetch_related` без `Prefetch()`
с явным queryset всё равно бьёт в БД заново.

`ProductDetailSerializer` — отдельно, с полным списком `variants`,
`images`, `description`, вложенным `shop` (мини-сериализатор с рейтингом).

#### 1.5 Фильтры, поиск, сортировка — `django-filter`, а не руками в `get_queryset`
```python
class ProductFilter(filters.FilterSet):
    category = filters.CharFilter(field_name="category__slug")
    min_price = filters.NumberFilter(field_name="base_price", lookup_expr="gte")
    max_price = filters.NumberFilter(field_name="base_price", lookup_expr="lte")
    shop = filters.CharFilter(field_name="shop__slug")
    in_stock = filters.BooleanFilter(method="filter_in_stock")

    def filter_in_stock(self, queryset, name, value):
        if value:
            return queryset.filter(variants__stock__gt=0).distinct()
        return queryset

    class Meta:
        model = Product
        fields = ["category", "shop"]
```
Обрати внимание на `filter_in_stock` — фильтр по связанной таблице
(`variants__stock__gt=0`) с `JOIN` может задублировать строки товара, если
у товара несколько подходящих вариантов, отсюда `.distinct()`. Без него
получишь один и тот же товар несколько раз в списке — баг, который легко
не заметить на тестовых данных с одним вариантом на товар, и вылезет
только на реальных данных.

`OrderingFilter` — `ordering_fields = ["base_price", "created_at"]`,
никогда не давай сортировать по произвольному полю без белого списка
(`ordering_fields = "__all__"` — плохая идея, через `?ordering=` можно
будет сортировать по внутренним/непроиндексированным полям и класть базу
на больших таблицах).
